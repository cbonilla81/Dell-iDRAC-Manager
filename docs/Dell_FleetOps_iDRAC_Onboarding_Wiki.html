Dell FleetOps iDRAC Manager

Production onboarding, Redfish inventory, firmware compliance and controlled updates

CentOS VM • Docker Engine CLI (no Docker Compose) • Repository v0.2 • October 2026

Repository: https://github.com/cbonilla81/Dell-iDRAC-Manager

Deployment context: /home/bonillac/githubrepo/Dell-iDRAC-Manager; frontend exposed on TCP 8080; Docker network idrac-network; persistent volume idrac_data.

1. Scope and critical safety boundaries

This runbook documents features described in the repository README. Verify exact endpoints and behavior against the checked-out commit before production use. No automatic network/subnet sweep is implemented: onboard each iDRAC by IP/DNS or automate explicit address imports through the API.

  • Stage 1: simulation and non-production verification.
  • Stage 2: live read-only inventory and firmware compliance scans.
  • Stage 3: one-server firmware pilot with explicit change approval.
  • Stage 4: small rolling batches with stop-on-failure, maintenance windows and rollback/recovery planning.
  • Never expose the unauthenticated HTTP management UI directly to the internet; enforce access control upstream and restrict network access.

2. Preconditions and topology

  • Supported Dell PowerEdge/iDRAC with working Redfish service (iDRAC9 or supported iDRAC8 firmware); confirm firmware/model compatibility.
  • CentOS Docker host can reach each iDRAC on TCP 443; iDRAC can reach approved firmware HTTPS repository on TCP 443.
  • Static/reserved iDRAC IPs or stable DNS, time synchronization, and correct management VLAN routing.
  • Separate read-only discovery account and privileged firmware update account where feasible; do not share personal admin credentials.
  • Maintenance approval, host/workload owner coordination, application failover and backup/restore tested before changes.

Connectivity and TLS checks

curl prompts for the password when --user has no colon/password. A successful -k test only proves connectivity, not certificate trust. Prefer valid iDRAC certificates and VERIFY_TLS=true; never place credentials on shell command lines or in shared logs.

3. Validate the running Docker deployment

The frontend Nginx must serve /usr/share/nginx/html/index.html and proxy /api/ to http://backend:8000/api/. The previously resolved HTTP 500 redirect loop was caused by an incorrect Nginx document root; preserve the corrected nginx.conf via image rebuild or read-only bind mount.

4. Protect secrets and prepare live mode

Confirm configuration without displaying secrets

The repository uses SECRET_KEY to encrypt stored iDRAC credentials. Keep the original key in a secure vault; rotating it without a migration will make previously encrypted credentials unreadable. Protect .env with chmod 600 and keep it out of Git. Verify the tracked repository does not contain real secrets.

Switch to real hardware only after simulation

Changing .env does not update an already-running container. Recreate only the backend using the same Docker network, alias, volume, image and --env-file; do not remove the named volume. Preserve any additional options from your current docker inspect output.

If the existing backend uses a different image tag or additional mounts, adapt the command. Verify /api/servers and logs after restart.

5. Prepare each iDRAC

  • Configure dedicated/shared iDRAC network interface, gateway, DNS and NTP.
  • Enable and test Redfish service under iDRAC settings (menu varies by generation).
  • Create a named service account with read-only rights for inventory. Confirm the account can GET Redfish endpoints.
  • Use a separate privileged account for updates; validate the exact privileges needed on the specific generation.
  • Install a trusted HTTPS certificate on iDRAC, or distribute the approved internal CA into the backend container trust store.
  • Record model, service tag, management IP, firmware version, location, business owner and maintenance group.

Redfish endpoints to validate

/redfish/v1/Systems/System.Embedded.1 — model, service tag, BIOS, power and health

/redfish/v1/Managers/iDRAC.Embedded.1 — iDRAC firmware

/redfish/v1/UpdateService/FirmwareInventory — installed component firmware

/redfish/v1/UpdateService/Actions/UpdateService.SimpleUpdate — update action; confirm support

/redfish/v1/TaskService/Tasks/ — task progress (task URI returned by action)

Redfish resource identifiers vary by model and firmware; discover links from /redfish/v1 rather than assuming every endpoint exists.

6. Add servers and collect inventory

UI: Open the FleetOps dashboard through your approved HTTPS reverse proxy/VPN. Select Add Server, enter friendly name, iDRAC IP/DNS and service-account credentials. Assign a group such as LAB, CANARY or PROD. Then run Scan. Verify model, service tag, BIOS, iDRAC version, health and power state.

API-based onboarding — authorized inventory only

For simple onboarding use the UI, which avoids storing passwords in a shell history or plaintext JSON file. The repository documents POST /api/servers, POST /api/servers/{id}/scan, GET /api/servers/{id}/firmware and GET /api/servers/{id}/preflight. Do not batch-add unapproved address ranges.

Read-only validation

Capture baseline inventory evidence, scan time, model, service tag and health state. Inventory results may differ by firmware version and installed hardware.

7. Firmware assessment and approved baselines

FleetOps does not automatically consult Dell Support, download the latest catalog or select firmware for you. Installed versions come from Redfish FirmwareInventory; approved target versions and HTTPS package URIs are administrator-defined.

  • Use Dell Support by service tag and Dell security advisories to determine appropriate firmware; consult release notes, prerequisites, sequencing and known issues.
  • Optionally use Dell Repository Manager to curate signed Dell Update Packages (DUPs) for specific models.
  • Host approved packages on an internal HTTPS repository reachable from iDRAC itself, not only from the CentOS VM.
  • Validate package provenance/signature, checksum, model applicability, supported upgrade path and storage/controller compatibility.
  • Create a baseline for the exact model and component name reported by inventory; record target version and approved HTTPS image URI.
  • Run compliance scan and review Compliant, Update Available and No Baseline outcomes; absence of a baseline is not compliance.

Example baseline concept (illustrative, not a verified Dell package): model PowerEdge R750; component BIOS; approved target version from Dell release notes; image URI https://firmware.example.internal/dell/APPROVED_PACKAGE.EXE. Confirm package compatibility and HTTPS reachability from iDRAC.

8. Controlled firmware update process

Change gate — all must pass

  • Written approval and maintenance window; affected hosts and workloads identified.
  • Recent application/data backup and tested recovery or host evacuation/failover procedure.
  • Healthy power, cooling, storage and network; no unresolved hardware faults.
  • Confirmed UPS/redundant power, stable iDRAC access, and access to out-of-band recovery.
  • Approved, verified firmware file reachable by iDRAC via HTTPS.
  • Validated exact model, service tag, component, current version and target version.
  • Documented expected reboot behavior, dependency ordering and downtime budget.
  • Pilot first on one non-production server; no fleet-wide action until evidence reviewed.

Pilot execution

1. Run Scan, Compliance and Preflight on one LAB server. 2. Verify the baseline and package URI. 3. Start a single-server rolling update from the FleetOps UI during an approved window. 4. Monitor job history and the returned Redfish TaskService URI. 5. Check iDRAC job queue and Lifecycle Controller where relevant. 6. Confirm any required reboot is coordinated and completed. 7. Rescan firmware, check health, service tag and workload availability. 8. Archive logs and approval evidence.

The repository exposes POST /api/rolling-update, but the exact request payload should be confirmed from the deployed FastAPI OpenAPI schema (/docs or /openapi.json) before scripting. Do not send an unverified update request.

Rolling production batches

Use small groups (for example, one server at a time per application failure domain), stop-on-failure, and explicit operator checkpoints between groups. Do not update both members of an HA pair together. Enforce the approved window outside the app if the current version only stores maintenance-window data but does not enforce it. Plan for updates that stage until reboot or require Dell-specific job queue handling.

9. Post-update acceptance and rollback

  • Confirm Redfish task/job outcome; a task accepted is not the same as firmware successfully installed.
  • Verify firmware inventory reports the approved target after any necessary reboot.
  • Verify power/health, storage controller, NIC links, boot, virtualization host state and application monitoring.
  • Compare against pre-change inventory and retain task URI, logs, versions and timestamps.
  • If failure occurs, stop the batch; do not blindly retry. Review Lifecycle Controller logs and Dell package notes.
  • Firmware downgrade/rollback is model- and component-dependent; do not assume every update can be reversed. Follow Dell-approved recovery procedures and engage support where appropriate.

10. Security hardening

  • Place FleetOps behind an authenticated TLS reverse proxy with SSO/MFA, access logging and management-subnet/VPN allowlisting.
  • Limit frontend TCP 8080 exposure; do not publish backend TCP 8000.
  • Separate read-only discovery identities from update-capable identities; rotate and vault credentials.
  • Set VERIFY_TLS=true with trusted iDRAC and firmware repository certificates. Avoid -k and strict-ssl false in production.
  • Use signed packages and verify hashes; do not host arbitrary URLs or allow unreviewed baseline edits.
  • Back up idrac_data and SECRET_KEY securely; test restoration.
  • Keep CentOS, Docker, base images and dependencies patched; scan images and pin trusted image versions.
  • Protect audit records; require change tickets, two-person approval for production and independent alerting on update failures.

12. Backup and recovery

Back up .env and SECRET_KEY separately in a protected vault. Test restoring the volume to an isolated environment. Avoid deleting or replacing idrac_data during container upgrades.

13. Operations checklist and acceptance criteria

  • Dashboard and /api/servers respond; Nginx configuration survives container recreation.
  • At least one non-production iDRAC scans with verified model/service tag/health.
  • TLS verification succeeds without bypasses.
  • Approved baseline yields an understandable compliance result.
  • One pilot firmware update is approved, tracked and verified after reboot if required.
  • Stop-on-failure and out-of-band recovery are rehearsed before rolling updates.
  • Backup/restore and change evidence are documented.
