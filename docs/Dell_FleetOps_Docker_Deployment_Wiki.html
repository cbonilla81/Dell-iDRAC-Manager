Dell-iDRAC-Manager — CentOS Docker Engine Deployment Runbook

Version: 1.0
Updated: October 2026
Repository: https://github.com/cbonilla81/Dell-iDRAC-Manager
Deployment method: Docker CLI only — no Docker Compose
Example source directory: /home/bonillac/githubrepo/Dell-iDRAC-Manager

Scope and assumptions: This runbook documents the deployment we troubleshot, not a guarantee that future repository revisions retain the same Dockerfiles, ports, environment variables, or API routes. Review the checked-out frontend/Dockerfile, backend/Dockerfile, frontend/nginx.conf, .env.example, and application documentation before deploying. Replace example addresses and paths with yours. Never commit secrets.

1. Architecture and prerequisites

  • CentOS Stream with supported Docker Engine, git, curl, openssl, and administrative privileges.
  • Two images/containers: React/Vite frontend served by Nginx on container TCP 80; Python/FastAPI backend on container TCP 8000 (verify current repository).
  • Dedicated user-defined Docker bridge network idrac-network; backend DNS alias backend for Nginx API proxy.
  • Named volume idrac_data mounted at /app/data to retain the backend database and application data.
  • Frontend published as 8080:80; backend port 8000 is not published to the host.
  • Network access to image registries and dependency repositories during builds; outbound HTTPS from backend to managed iDRACs when live mode is enabled.
  • Keep the dashboard on an authorized management network or VPN. HTTP 8080 is for controlled lab access; add HTTPS and authentication before production use.

2. Preflight checks

cat /etc/os-release
uname -m
pwd
sudo docker version
sudo systemctl is-active docker
sudo firewall-cmd --state || true
getenforce 2>/dev/null || true

If Docker is not installed on a supported CentOS Stream release:

sudo dnf install -y dnf-plugins-core git curl openssl
sudo dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
sudo dnf install -y docker-ce docker-ce-cli containerd.io
sudo systemctl enable --now docker
sudo docker run --rm hello-world

Gotcha: CentOS Linux 7/8 are end-of-life. Do not assume current Docker packages work there; migrate to a supported OS. A sudo docker command avoids Docker socket permission issues without adding users to the effectively root-equivalent docker group.

4. Configure secrets and simulation mode

Inspect .env.example and the backend application to confirm the exact supported variable names before proceeding.

cd /home/bonillac/githubrepo/Dell-iDRAC-Manager
cp -n .env.example .env
openssl rand -hex 48
sudo vi .env
sudo chmod 600 .env

Example settings used during troubleshooting (verify against the current repository):

SECRET_KEY=REPLACE_WITH_GENERATED_SECRET
SIMULATION_MODE=true
VERIFY_TLS=false
REQUIRE_MAINTENANCE_WINDOW=false

Security gotchas: Prefer VERIFY_TLS=true for real iDRACs with valid certificates; disabling iDRAC TLS verification is not a general solution to npm's TLS errors. Start with SIMULATION_MODE=true and validate behavior before any live management actions. Store the SECRET_KEY in a secure backup: changing it may make encrypted stored credentials unreadable. Avoid printing or committing .env.

5. Create Docker network and persistent storage

sudo docker network inspect idrac-network >/dev/null 2>&1 || sudo docker network create idrac-network
sudo docker volume inspect idrac_data >/dev/null 2>&1 || sudo docker volume create idrac_data
sudo docker network inspect idrac-network
sudo docker volume inspect idrac_data

Gotcha: Do not run docker volume rm idrac_data during upgrades or troubleshooting. This volume may hold your database and encrypted credentials.

6. Build images — Docker CLI only

cd /home/bonillac/githubrepo/Dell-iDRAC-Manager
sudo docker build -t idrac-backend:0.2 ./backend
sudo docker build -t idrac-frontend:0.2 ./frontend
sudo docker image ls

Confirm the frontend Dockerfile performs the Node build and copies the actual Vite output to Nginx's web root. For a standard Vite build, the final stage typically includes:

COPY --from=build /app/dist/ /usr/share/nginx/html/
COPY nginx.conf /etc/nginx/conf.d/default.conf

The source stage name and output path must match your actual Dockerfile/Vite configuration.

npm TLS failure: UNABLE_TO_GET_ISSUER_CERT_LOCALLY

Typical failure:

npm error code UNABLE_TO_GET_ISSUER_CERT_LOCALLY
request to https://registry.npmjs.org/@vitejs%2fplugin-react failed

Check host TLS and DNS first:

curl -Iv https://registry.npmjs.org/
getent ahostsv4 registry.npmjs.org
echo | openssl s_client -connect registry.npmjs.org:443 -servername registry.npmjs.org 2>&1 | grep -E 'subject=|issuer=|Verify return code'

In the troubleshooting session, DNS returned 146.112.49.0, associated with Cisco Umbrella/OpenDNS infrastructure. That is a clue to inspect DNS security or filtering, not proof of SSL inspection. If the registry is blocked by policy, a CA certificate alone will not fix the block.

Preferred solutions: (1) obtain and install your organization's approved CA chain into the CentOS trust store and the Node build image; (2) use an approved internal npm registry; or (3) build on another trusted machine and transfer the image. Do not permanently set strict-ssl=false or NODE_TLS_REJECT_UNAUTHORIZED=0 for production builds.

If building elsewhere on the same CPU architecture:

# On trusted build machine:
docker build -t idrac-frontend:0.2 ./frontend
docker save -o idrac-frontend.tar idrac-frontend:0.2
scp idrac-frontend.tar USER@CENTOS_HOST:/tmp/
# On CentOS VM:
sudo docker load -i /tmp/idrac-frontend.tar

Verify architecture compatibility with uname -m on both systems. The build machine must have permission to access the dependencies; do not circumvent organizational security controls.

7. Start backend and frontend

cd /home/bonillac/githubrepo/Dell-iDRAC-Manager
sudo docker run -d \
  --name idrac-backend \
  --hostname backend \
  --network idrac-network \
  --network-alias backend \
  --restart unless-stopped \
  --env-file .env \
  --mount source=idrac_data,target=/app/data \
  idrac-backend:0.2

sudo docker run -d \
  --name idrac-frontend \
  --network idrac-network \
  --restart unless-stopped \
  -p 8080:80 \
  --mount type=bind,src=/home/bonillac/githubrepo/Dell-iDRAC-Manager/frontend/nginx.conf,dst=/etc/nginx/conf.d/default.conf,readonly \
  idrac-frontend:0.2

Why bind-mount nginx.conf? It keeps the corrected Nginx configuration persistent across frontend container replacement, even if the image still contains an older configuration. On SELinux-enforcing CentOS, a bind mount can be denied due to labeling. For a single-file mount, first try the -v /absolute/path/nginx.conf:/etc/nginx/conf.d/default.conf:ro,Z syntax instead of --mount (Docker's :Z labeling option applies to -v bind mounts). This may relabel the source file; for a safer long-term deployment, bake the configuration into a rebuilt image. Never label arbitrary system directories.

If you already have an existing frontend container, don't run a second container with the same name. See the replacement procedure below.

8. Correct Nginx config — confirmed fix for HTTP 500

The working frontend image contained /usr/share/nginx/html/index.html and assets/, yet requests to / returned 500 with:

rewrite or internal redirection cycle while internally redirecting to "/index.html"

The active configuration lacked an explicit document root. Use this Nginx configuration, preserving the backend proxy:

server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    location /api/ {
        proxy_pass http://backend:8000/api/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}

To edit a root-owned file without -bash: nginx.conf: Permission denied:

cd /home/bonillac/githubrepo/Dell-iDRAC-Manager/frontend
sudo cp nginx.conf nginx.conf.bak
sudo tee nginx.conf >/dev/null <<'EOF'
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;
    location /api/ {
        proxy_pass http://backend:8000/api/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
    location / { try_files $uri $uri/ /index.html; }
}
EOF

For an already-running container without the bind mount, apply without rebuilding:

sudo docker cp nginx.conf idrac-frontend:/etc/nginx/conf.d/default.conf
sudo docker exec idrac-frontend nginx -t
sudo docker exec idrac-frontend nginx -s reload
curl -I http://localhost:8080/

Gotcha: docker cp is a temporary container modification. Recreating the container loses it. Persist the fix via the corrected Dockerfile/image or a read-only bind mount.

9. Verify and open the application

sudo docker ps -a
sudo docker logs --tail 100 idrac-frontend
sudo docker logs --tail 100 idrac-backend
sudo docker exec idrac-frontend ls -lah /usr/share/nginx/html/
sudo docker exec idrac-frontend nginx -t
curl -I http://localhost:8080/
curl -i http://localhost:8080/api/servers

Expected frontend: HTTP 200 and index.html plus assets/ present. The /api/servers endpoint should return an appropriate API response if that route exists in the checked-out revision; 404 may indicate a route mismatch, not necessarily a failed backend.

Open http://CENTOS_VM_IP:8080 from a permitted management workstation. If firewalld is active, allow 8080 only from trusted networks (use a rich rule or zone/source restriction rather than broadly exposing the port).

11. Safe updates and rollback

Before changes, record the currently running images and preserve your source configuration:

sudo docker inspect idrac-frontend --format '{{.Config.Image}}'
sudo docker inspect idrac-backend --format '{{.Config.Image}}'
sudo docker image ls
sudo docker volume inspect idrac_data

Build new versioned images (e.g. idrac-frontend:0.3), test build success, then stop/remove only the frontend container and start the new image with the same network, port and read-only Nginx bind mount. For rollback, recreate the frontend with the previous image tag. Do not remove the backend or volume to resolve frontend issues.

12. Backups and recovery

For a consistent backup, temporarily stop backend writes:

sudo mkdir -p /opt/idrac-backups
sudo docker stop idrac-backend
sudo docker run --rm \
  -v idrac_data:/data:ro \
  -v /opt/idrac-backups:/backup \
  alpine tar czf /backup/idrac_data_backup.tar.gz -C /data .
sudo docker start idrac-backend

Back up .env separately to an access-controlled secret store; preserve the original SECRET_KEY. Test restores on a nonproduction VM. Do not overwrite an active production volume. A restore into a new volume can be staged using an Alpine container, then verified before cutover.

13. Production hardening checklist

  • [ ] Supported CentOS release and patched Docker Engine.
  • [ ] Source revision/tag documented; images built from known dependency versions.
  • [ ] Verified CA trust; no permanent npm TLS bypass.
  • [ ] Nginx serves React files and proxies API correctly.
  • [ ] HTTPS termination and authentication/SSO in front of dashboard.
  • [ ] Port 8080 restricted to trusted management network/VPN.
  • [ ] Backend port 8000 not exposed publicly.
  • [ ] SECRET_KEY secured and backed up; .env excluded from Git.
  • [ ] iDRAC accounts least privilege; validate TLS for production iDRAC connections.
  • [ ] Simulation mode tested before enabling real operations.
  • [ ] Firmware updates gated by approvals, maintenance windows and tested recovery plans.
  • [ ] Named volume backed up and restore tested.
  • [ ] Container restart policies and log retention reviewed.
